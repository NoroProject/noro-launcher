# Выпуск и деплой

Три workflow, три разных триггера — порядок между ними важен, потому что мастер
и лаунчер собираются независимо, а раздаёт лаунчер мастер.

| Workflow | Триггер | Что делает |
|---|---|---|
| `docker.yml` | push в `master`/`main`, тег `v*` | образ мастера в ghcr (amd64 + arm64) |
| `release-launcher.yml` | тег `launcher-v*` | бинарники лаунчера в GitHub Release |
| `release-master.yml` | тег `master-v*` | бинарники мастера в GitHub Release |

Мастер лаунчер **не компилирует**: `launcher_builder` забирает готовые ассеты
релиза по тегу, подписывает их ed25519 и кладёт в FileStore. Поэтому без Actions
новую версию лаунчера выпустить нечем — это единственный путь.

## Порядок

1. `git push origin master` — поехал `docker.yml`, собирается образ мастера.
2. Задеплоить мастер на прод: подтянуть новый образ и перезапустить.
3. Тег `launcher-v<версия>` и push тега — `release-launcher.yml` собирает core и
   bootstrapper под все пять платформ и вешает на релиз.
4. В админке запустить сборку лаунчера для этого тега: мастер скачает ассеты,
   подпишет и начнёт раздавать через `/api/launcher/version`.
5. Опубликовать сборку в админке — пересоберётся и переподпишется манифест.

Шаги 1–2 и 3–4 независимы, но если правки затронули формат манифеста, мастер
должен обновиться раньше, чем клиенты получат новый core.

## Bootstrapper обновляется только руками

`crates/noro_launcher` — тот самый файл, который «НИКОГДА не обновляется после
первой установки»: так на Windows копится репутация SmartScreen. Мастер его
раздаёт только новым установкам, у существующих он остаётся прежним навсегда.

Правки в bootstrapper (окно загрузки, проверка подписи, запуск core) до уже
установленных копий не доедут — их нужно переустанавливать. В разработке это
просто замена своего локального бинарника.

## Разовое: сбросить base build со свёрнутыми правилами

До 1.3.1 мастер вычислял `rules` из version.json у себя и складывал в
`base_builds` уже отфильтрованные аргументы — под ОС того, где шёл bootstrap.
Сборка, забутстрапленная на macOS, несёт `-XstartOnFirstThread`, от которого JVM
на Linux и Windows не стартует; забутстрапленная на Linux-сервере — наоборот,
теряет его для macOS.

Теперь правила доезжают до клиента невычисленными, но **старые строки сами не
починятся**: `ensure_base_build` при существующей записи делает `return`. Такую
запись надо удалить один раз, после чего опубликовать сборку заново.

Найти свёрнутые (в аргументах нет ни одного объекта с `rules`):

```sql
SELECT id, mc_version, modloader, jsonb_typeof(jvm_args -> 0) AS first_arg
FROM base_builds
WHERE NOT jvm_args @> '[{}]';
```

Удалить — `base_build_files` уйдут каскадом:

```sql
DELETE FROM base_builds WHERE id = '<id>';
```

Дальше «опубликовать» в админке. Файлы заново не качаются: стор адресуется по
содержимому, и `put_url` пропускает всё, что уже лежит, — время уйдёт только на
повторную прогонку installer'а Forge/NeoForge.

Проверить, что формат новый:

```sql
SELECT jsonb_path_query_array(jvm_args, '$[*] ? (@.rules != null)')
FROM base_builds;
```

Должны появиться объекты с `rules` — например `-XstartOnFirstThread` под
`{"os": {"name": "osx"}}`.
