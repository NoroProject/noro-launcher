# Дела: репорты, наказания и разбор в игре

Репорт сегодня — строка в очереди: кто, на кого, координаты, статус. Разбор
живёт в голове модератора, а доказательства — в его памяти. План превращает
репорт в **дело**: карточку, где лежит всё, чем модератор пользовался, и по
которой через полгода видно, за что человека наказали.

Развилки приняты 2026-08-20 и переспрашивать их не надо.

| Развилка | Решение |
|---|---|
| Чат-лог | Кольцевой буфер в агенте, в дело уезжает срез вокруг события |
| Что в срезе | Публичный чат + ЛС участников + команды цели |
| Сущность | Отдельная таблица `cases`, репорты складываются в дело |
| Кто ведёт | Сайт и игра равноправны, замок на одного модератора |
| Ложные репорты | Счётчик подтверждённых, наказание по п.2.4 — руками |
| Порядок | Одной волной: мастер + веб + агент |

## Схема

```sql
cases (id, target_id, game_server_id, status, claimed_by, claimed_at,
       opened_at, resolved_at, verdict, rule_id, rule_code, resolution)
player_reports + case_id           -- репорт складывается в дело
case_events (id, case_id, at, actor_id, source, kind, payload JSONB)
case_messages (id, case_id, at, sender_id, sender_name, channel, content)
```

`status`: `open` → `in_review` (кто-то взял) → `resolved` | `rejected`.
Наказание не колонкой: `punishments.case_id` — за одно дело их бывает
несколько (мут за чат и бан за чит одним разбором).

`case_events.kind` — лента разбора: `report_added`, `claimed`, `released`,
`teleport`, `freeze`, `watch_start`, `inventory_snapshot`, `chat_slice`,
`client_check`, `note`, `punishment`, `verdict`, `feedback_sent`. `source` —
`web` или `game`: по ленте должно быть видно, откуда действовали.

`case_messages.channel` — `public`, `local`, `private`, `command`. Команды из
списка аутентификации (`/login`, `/register`, `/l`, `/reg`, `/changepassword`)
**не пишутся вовсе** — иначе в деле оказывается чужой пароль.

Репутация репортера не хранится: `count(*) filter (where verdict = ...)` по его
делам считается запросом, строк на игрока десятки.

## Права

```
noro.mod.cases.view       очередь и карточка
noro.mod.cases.claim      взять в работу
noro.mod.cases.resolve    закрыть с вердиктом
noro.mod.cases.chat       видеть срез чата (отдельно: там ЛС)
noro.mod.cases.inventory  осмотр инвентаря цели
noro.mod.cases.watch      слежка за целью
noro.mod.cases.client     запрос проверки клиента
```

Существующие `noro.mod.reports.*` остаются: очередь репортов — вход в дело.

## Протокол

`ToAgent` (мастер → агент):

- `CaseAssigned { case, target, reporter, place, reason, moderator }` — модер
  взял дело на сайте; агент шлёт ему меню, если он в игре;
- `CaseReleased { case }`, `CaseClosed { case, verdict }`;
- `CaseChatRequest { case, target, before_secs, after_secs }`;
- `CaseInventoryRequest { case, target }`.

`FromAgent` (агент → мастер):

- `CaseClaim { case, moderator }` — взял из игры, мастер проверяет замок;
- `CaseAction { case, kind, payload }` — тп, заморозка, ваниш, слежка;
- `CaseChatSlice { case, messages[] }`, `CaseInventory { case, items[] }`.

Замок — на мастере: `claimed_by` ставится одним `UPDATE ... WHERE claimed_by IS
NULL`. Кто проиграл гонку, получает «уже занято», а не второе меню.

## Агент: режим разбора

`ChatRing` — кольцевой буфер на сервер, последние ~300 сообщений с временем,
отправителем и каналом. В БД не уезжает ничего, пока не появился повод.

Вход в режим (`CaseAssigned` или `/case claim <id>`):

1. позиция и игровой режим запоминаются — выход возвращает как было;
2. ваниш включается (готовый механизм п.43);
3. в чат уходит меню Adventure-компонентами: **тп к месту**, **тп к цели**,
   **тп к репортеру**, **назад**, **чат цели**, **инвентарь**, **слежка**,
   **заморозить**, **наказать по пункту**, **закрыть дело**;
4. цель и репортер подсвечиваются через стены разными цветами — свечение
   видно только модератору в режиме, точка микширования та же, что у ваниша;
5. каждое действие уходит кадром `CaseAction` и появляется в ленте на сайте.

Слежка — spectator с привязкой к цели: killaura и fly скриншотом не докажешь.
Осмотр инвентаря — снимок предметов в дело, без права правки.

## Веб

`/admin/cases` — очередь: цель, сколько репортов, кто ведёт, сколько висит,
репутация репортеров. Карточка дела — три колонки: лента событий, срез чата с
фильтром каналов, панель действий (взять, наказать по вилке свода, закрыть).

Наказание выдаётся формой, которая уже умеет вилки (`usePunishForm`), но
`rule_code` подставляется из дела. Закрытие дела с вердиктом `confirmed`
отправляет репортеру обратную связь — механизм `pending_report_feedbacks` есть.

Лента обновляется опросом раз в 5 секунд, пока карточка открыта: WebSocket у
мастера сейчас только для лаунчера, агента и враппера, и ради одной страницы
заводить четвёртый не стоит.

## Предлагаю сверх заказанного

Не решено — на ваше усмотрение:

1. **Авто-склейка.** Новый репорт на ту же цель в течение 6 часов падает в
   открытое дело, а не заводит второе. Семь жалоб на читера — одна карточка.
2. **Возврат в очередь.** Модератор ушёл с сервера или не трогал дело 15 минут
   — замок снимается сам, дело возвращается в очередь.
3. **Приоритет.** Дело поднимается по числу *разных* репортеров и по тяжести
   пункта свода: пять человек про чит важнее одной жалобы на мат.
4. **Повторник.** Если у цели есть закрытые дела с `confirmed`, карточка
   говорит об этом, а форма наказания предлагает вилку «повторное».
5. **Автомодерация в деле.** Срабатывания фильтров чата (`automod_triggers`) по
   этой цели показываются в ленте: жалоба на оскорбления рядом с тем, что
   фильтр уже поймал.
6. **Дело в кабинете наказанного.** Игрок видит своё дело: пункт, срок,
   вердикт, срез чата — без имени репортера и без чужих ЛС. Апелляция
   перестаёт быть спором на память.
7. **Кулдаун по репутации.** У кого доля подтверждённых жалоб высокая — минута
   между репортами, у кого низкая — час.
8. **Сигнал в Discord**, если открытое дело висит без модератора онлайн.

## Сделано 2026-08-20

1. миграция `0061_cases.sql`, права `noro.mod.cases.*`, замок одним UPDATE;
2. API: очередь, карточка, claim/release/resolve, заметки, запросы к игре;
3. кадры в обе стороны: `case_assigned`/`case_finished`/`case_chat_request`/
   `case_inventory_request` и обратно `case_claim`/`case_action`/
   `case_chat_slice`/`case_inventory`;
4. веб: `/admin/cases` и карточка с лентой, срезом чата и формой наказания.
   Отдельный пункт «Жалобы» убран — жалоба всегда лежит в деле, и две очереди
   были двумя входами в один список; `/admin/reports` остался редиректом;
5. агент: `ChatRing`, меню разбора кликабельными кнопками (`cmd:`-ссылки),
   ваниш, телепорты, слежка через spectator, снимок инвентаря;
6. наказание из дела и из игры встаёт в ленту, закрытие рассылает авторам
   жалоб обратную связь.

**Подсветки участников через стены пока нет.** Свечение, видимое одному
зрителю, требует подмены пакета — той же точки микширования, что и ваниш.
Ванильный `setGlowing` светит всем, и нарушитель узнал бы о разборе раньше
модератора, поэтому платформы честно отвечают «не умею».

Выкладка — общий релиз мастера, веба и агента: агент собирается отдельно и
раскатывается на сервер вручную (см. [agents.md](./agents.md)).
