# План развития агента

Продолжение [agents.md](./agents.md): там описано то, что уже работает, здесь —
что решено добавить и в каком порядке. Решения по развилкам приняты 2026-08-18,
переспрашивать их не нужно; всё, что помечено «открыто», — не решено сознательно.

Обозначения: **[А]** агент (`agent/core` + платформы), **[М]** мастер
(`crates/master`), **[В]** веб (`web/`), **[Л]** лаунчер (`crates/frontend`,
`crates/backend`), **[W]** ServerWrapper.

## Принятые решения

| Тема | Решение |
| --- | --- |
| Автомодерация чата | Режим настраивается **на каждый фильтр** в админке: отказ / эскалация / мут сразу / только сигнал |
| Что фильтруем | Реклама (IP, домены, инвайты), мат по словарю из админки, капс и флуд, обход через гомоглифы/leet/разрядку |
| `/freeze` | Блокируются движение, команды и урон; **чат остаётся** — модератору нужно, чтобы игрок мог ответить. Держится до `/unfreeze`, переживает релог |
| Репорты | Очередь в админке **и** сигнал онлайн-стаффу в игре, с координатами и телепортом к месту |
| Онлайн | Публичный список, но у игрока есть тумблер «скрыть меня»; стафф видит всех. Плюс heatmap активности по дням, как коммиты на GitHub |
| Игровое время | Хранить **сессии целиком** (вход, выход, сервер) |
| Язык сообщений | Язык клиента MC, фолбэк на язык профиля |
| Экран бана | Причина, срок, кто выдал, пункт свода с названием, ID для апелляции, ссылка на свод |
| Расписание рестартов | Простой конструктор (время / интервал) **и** cron для сложных случаев |
| Рестарт при онлайне | Политика задаётся **на каждое расписание** отдельно |
| Авто-рестарт по TPS | Просадка — только алерт. Рестарт — лишь при полном зависании (тик не двигался N секунд) |
| Техработы | Выбор в момент включения: «закрыть вход» или «закрыть и выгнать» |
| Флаг целостности | Исполняется действие из `blocked_files`: `BlockLaunch` — не пускать, `Flag` — пустить и сообщить стаффу, `Delete` — молча |
| Действия из админки в игру | Кик, личное сообщение, объявление. Консольную команду через агент **не** добавляем |
| Принудительные действия лаунчера | Своё право на каждое действие |
| Уведомление о принудительном действии | Решает админ галкой в момент действия; «тихо» — под отдельным правом |
| Ваниш | Микшины на модах, видимость по весу роли, полное отсутствие в мире и в онлайне; подробности — в разделе п.43 |

## Что меняется в контракте

Это ядро плана: почти каждый пункт ниже опирается на один из этих четырёх сдвигов.

### 1. Канал `/api/agent/link` становится двусторонним

Сейчас `ToAgent` знает три кадра, а `AgentLink.java` умеет только принимать.
Добавляется `FromAgent` — и это единственное принципиальное изменение
архитектуры во всём плане.

```
FromAgent (агент → мастер)          ToAgent (мастер → агент)
  player_join   uuid, ip_hash         profile_changed  uuid | null (null — всем)
  player_leave  uuid, reason          kick             uuid, message
  chat_hit      uuid, filter, text    tell             uuid, message
  report        payload               announce         message
  tick_stall    stalled_secs          freeze / unfreeze uuid, by, reason
                                      maintenance      on/off, message, kick_online
                                      restart_notice   at, reason
                                      filters_changed
```

**Событие — не источник истины.** Канал рвётся, кадры теряются; поэтому
heartbeat начинает нести **полный список UUID онлайна**, и мастер сверяет
состояние по нему, а события использует только чтобы реагировать быстро.
Иначе после каждого обрыва в базе оставались бы вечно живые сессии.

### 2. Heartbeat расширяется

```json
{ "online": 12, "max_players": 60, "version": "Paper 1.21.1",
  "agent_version": "1.7.3", "tps": 19.8, "mspt": 41.2,
  "heap_used_mb": 6114, "heap_max_mb": 12288, "uptime_secs": 51244,
  "players": ["95bf010b-…", "…"], "vanished": ["…"] }
```

`vanished` отделён от `players` ради ваниша (п.43): публичное число считается по
первому, а сессии — по обоим, иначе мастер закроет сессию скрытого модератора,
решив, что тот вышел.

Все поля, кроме первых трёх, необязательны: старый агент продолжает работать
с новым мастером, и наоборот.

### 3. `AgentPlayer` дополняется

```rust
pub active_ban: Option<AgentPunishmentSummary>,  // симметрично active_mute
pub locale: Option<String>,                      // язык профиля, фолбэк для п.15
pub frozen: Option<FreezeInfo>,                  // заморозка переживает рестарт
pub integrity: Option<IntegrityVerdict>,         // действие из blocked_files
```

`active_ban` — то, чего сейчас не хватает больше всего: агент знает
`banned: bool` и не может показать ни причины, ни срока.

### 4. TPS агент считает сам

Не через `getAverageTickTime()` и не через `Bukkit.getTPS()`: на диапазоне
1.18 → 26.x эти API разъезжаются, и каждая версия — ещё одна директива
препроцессора. Вместо этого `TickMeter` в `core` считает тики по хуку конца
тика, который есть на всех платформах (Fabric `ServerTickEvents`, Forge/NeoForge
`ServerTickEvent`, Paper `runTaskTimer`).

Побочная выгода важнее основной: `lastTickAt` обновляется из игрового потока, а
читает его фоновый демон. Если игровой поток встал — счётчик замер, а сообщить
об этом всё ещё есть кому. Это и есть детектор зависания для п.39.

## Порядок работ

Волны выстроены по зависимостям, а не по важности. Внутри волны пункты
независимы.

- **Волна 0 — фундамент.** Двусторонний канал, `active_ban`, `locale`,
  `TickMeter`. Без неё половина остального не делается.
- **Волна 1 — то, что видит игрок.** 13 (экран бана), 15 (язык), 1 (`/rules`),
  4 (`/check`), 14 (профиль на лету).
- **Волна 2 — присутствие.** 5 (онлайн), 6 (сессии, heatmap), 7 (телеметрия),
  8 (действия из админки).
- **Волна 3 — модерация.** 32 (freeze), 11+34 (репорты), 10 (автомодерация),
  43 (ваниш — самый рискованный пункт плана, см. раздел).
- **Волна 4 — эксплуатация.** 17+37 (расписания), 38 (бэкапы), 39 (зависание),
  40 (причина падения), 25 (техработы).
- **Волна 5 — доступ.** 24 (целостность).
- **Отдельная дорожка.** Принудительные действия лаунчера — агента не касаются
  вовсе, можно делать в любой момент.

## Волна 0. Фундамент

### 0.1 Двусторонний канал [А][М]

**Мастер.** `agent_link/proto.rs`: рядом с `ToAgent` появляется `FromAgent`
(`#[derive(Deserialize)]`, тот же `tag = "type"`). `session.rs` начинает читать
входящие кадры — сейчас он их игнорирует. Обработчики — отдельным модулем
`agent_link/inbox.rs`, чтобы сессия осталась про сокет.

**Агент.** `AgentLink` получает `send(FromAgent)` с очередью: `WebSocket.sendText`
нельзя звать до завершения предыдущего — та же проблема, что уже решена в
`wrapper/Outbox.java`, и решение оттуда переиспользуется.

**Что важно не сломать:** канал не обязателен. Всё, что уходит наверх, — либо
дублируется heartbeat'ом (онлайн), либо переживает потерю (сигнал стаффу). Ни
одно решение агента не должно ждать ответа мастера по этому каналу.

### 0.2 `active_ban`, `locale`, `frozen`, `integrity` в профиле [М]

`api/agent/player.rs` уже дёргает `active_punishments` — активный бан берётся
оттуда же, где активный мут. `locale` — из профиля пользователя.

### 0.3 `TickMeter` [А]

`core/TickMeter.java`: `onTick()` из игрового потока, `tps()`, `mspt()`,
`stalledSeconds()` — снаружи. Платформенные вызовы — три строки в существующих
точках входа.

## Волна 1. То, что видит игрок

### п.13 Экран бана из шаблонов админки [А][М]

**Проблема.** `AccessGate.java:46-48` отдаёт литерал `"You are banned on this
network."`. Шаблоны `ban_permanent` / `ban_temporary` правятся в
`/admin/moderation` и срабатывают только если игрок был онлайн в момент бана.
Забаненный вчера видит сухую строку.

**Решение.** `AccessGate` перестаёт возвращать готовый текст и возвращает
причину отказа как данные (`Denial { kind, punishment, profile }`). Рендерит
платформа — тем же `MessageRender`, что уже рисует кик при живом бане.

**Состав экрана** (решено): причина, срок, кто выдал, пункт свода с названием,
ID наказания, ссылка на свод и апелляцию. Всё это уже есть в подстановках
`MessageRender` — кроме `{rule_title}`, который приходит из `RuleCatalog`.

**Тонкость.** Отказы бывают четырёх видов, и шаблон нужен каждому: бан сети,
бан сервера, «нет аккаунта на мастере», «нет доступа к сборке». Сейчас в
`ModerationMessages` есть только первые два — добавляются `no_account` и
`no_access`.

**Готово, когда:** забаненный игрок при попытке входа видит текст, набранный в
админке, с причиной, сроком и ID; правка текста в админке видна без перезапуска
игрового сервера.

### п.15 Язык клиента [А][М]

**Источник языка:** локаль клиента MC, фолбэк — `locale` из профиля.
Клиент сообщает язык в `ClientInformation` (Paper: `Player.getLocale()`), но
**на экране отказа его ещё нет** — там работает только фолбэк, ради него
`locale` и появился в профиле.

**Где живут строки.** Шаблоны наказаний в `instance_settings` становятся
словарём по языкам: `{"en": {...}, "ru": {...}}`, с фолбэком на `en`. Свод
правил уже переведён (`rule_translations`) — `/api/agent/rules` начинает
принимать `?lang=`.

**Строки самого агента** («You can speak again», ошибки команд, usage) уезжают
в `core/AgentStrings.java` — простая карта, никакой библиотеки i18n в агенте.
Модератор получает ответы на языке своего клиента.

**Готово, когда:** русский игрок видит причину бана и текст правила по-русски,
английский — по-английски, а сборка без перевода откатывается на английский без
пустых строк.

### п.1 `/rules [код]` [А]

`RuleCatalog` уже держит коды, названия и формулировки наказаний. Команда
показывает дерево свода, а с кодом — конкретный пункт с кликабельной ссылкой
(`TextMarkup` это умеет). Прав не требует: свод публичный.

Заодно — `{rule}` в текстах наказаний становится кликабельным и открывает
`/rules <код>` через `run_command`.

### п.4 `/check <ник>` [А]

Карточка: роли с иконками, активный мут с остатком, активный бан, число варнов,
сколько наиграл, когда заходил в последний раз, флаг целостности (п.24).
Данные — один `playerByName`, всё уже в профиле; playtime и последний вход
добавятся в профиль вместе с волной 2.

Право — существующее `noro.mod.punish.view`. Отдельный узел не заводим: кто
видит историю наказаний, видит и карточку.

### п.14 Профиль на лету [А][М]

**Проблема.** `ProfileCache` наполняется на логине, чистится на выходе;
обновляются только муты. Выдали роль на сайте — в игре ничего не изменится до
перезахода.

**Решение.** Кадр `profile_changed { uuid }` (или `null` — «перечитать всех»)
при изменении ролей, прав, префиксов. Агент перечитывает профиль и заново
раскладывает права и префикс, ничего не спрашивая у игрока.

**Откуда шлётся:** мастер уже знает все точки правки — админка ролей, прав,
пользователей. Один вызов рядом с записью в БД.

**Тонкость.** Перечитывание всех при `null` на сервере с сотней игроков — сто
запросов подряд. Поэтому у агента батч-эндпоинт `POST /api/agent/players/batch`
со списком UUID, и обновление идёт одним запросом.

## Волна 2. Присутствие

### п.5 Поимённый онлайн [А][М][В]

**Транспорт.** События `player_join` / `player_leave` — для скорости, полный
список в heartbeat — для истины (см. «Что меняется в контракте»).

**Приватность.** `users.hide_from_online` — тумблер в кабинете. Скрытый игрок
**считается в числе** онлайна и виден стаффу: иначе счётчик разъедется с
реальностью, а тумблер станет способом прятаться от модерации.

**Веб.** Публично — список на странице сервера. В админке — список с кнопками
кика и сообщения (п.8).

**Готово, когда:** на странице сервера виден состав, скрывшийся игрок пропадает
из публичного списка, но число не меняется, а после обрыва канала список
сходится в течение одного heartbeat.

### п.6 Сессии и heatmap [М][В]

**Схема.** `player_sessions (id, user_id, game_server_id, started_at, ended_at,
end_reason)`. Плюс производная `player_activity_days (user_id, day, minutes)` —
её пересчитывает мастер при закрытии сессии, чтобы heatmap не агрегировал
таблицу сессий на каждый показ страницы.

**Незакрытые сессии — главная сложность.** Сервер упал, канал оборвался, агента
перезапустили: `ended_at` никто не проставит. Закрывает мастер, по последнему
heartbeat этого сервера, с `end_reason = 'lost'`. Фоновая задача рядом с
существующей `expire_punishments`.

**Heatmap.** Квадратики по дням за год, как коммиты на GitHub: чем больше
наиграно за день, тем ярче. Живёт в профиле игрока на сайте; порог яркости —
относительный (доля от личного максимума), иначе у новичка вся сетка серая.

**Готово, когда:** профиль показывает суммарное время, дату последнего входа и
годовую сетку; убийство процесса сервера не оставляет открытых сессий.

### п.7 Телеметрия сервера [А][М][В]

Из `TickMeter` и `Runtime` — в heartbeat. Хранится в `server_telemetry` с
коротким TTL (сырые точки — 7 дней, дальше — часовые агрегаты).

**Веб:** график TPS и памяти на `StatusPanel.vue`, плюс отметка «сервер лагает»
в списке серверов. Сейчас лагающий и здоровый сервер выглядят одинаково.

### п.8 Действия из админки в игру [А][М][В]

Три кадра: `kick`, `tell`, `announce` — ровно то, что уже умеет `GameBridge`.
Консольную команду через агент **не добавляем**: для этого есть консоль враппера,
а второй путь исполнения произвольных команд — вторая дверь с теми же ключами.

Права: `noro.admin.game.kick`, `noro.admin.game.tell`, `noro.admin.game.announce`.
Все три действия пишутся в аудит с указанием актора — как и наказания.

## Волна 3. Модерация

### п.32 `/freeze` [А][М]

**Что запрещено:** движение, команды, урон. Чат остаётся — половина разборов
заканчивается объяснением, и лишать игрока речи в этот момент бессмысленно.

**Как держится движение.** Не эффектами и не флагами: агент запоминает позицию
и возвращает игрока на неё на каждом тике, если тот сдвинулся. Это одно решение
на все платформы, и оно же закрывает телепорт — включая `/home`, который на
Fabric иначе не перехватить (см. «Ограничения»).

**Урон:** `Entity.setInvulnerable(true)` — ванильный метод, одинаковый на всём
диапазоне. Замороженного нельзя убить, пока идёт разбор.

**Команды:** те же хуки, что и мут (`PlayerCommandPreprocessEvent` на Paper,
`CommandEvent` на Forge/NeoForge, `ALLOW_COMMAND_MESSAGE` на Fabric).

**Состояние — на мастере**, таблица `player_freezes`. В памяти агента заморозка
пережила бы релог, но не рестарт сервера, а «перезашёл — разморозился» делает
инструмент бесполезным. Приходит кадром и в профиле, снимается `/unfreeze`.

Право: `noro.mod.freeze`. Заморозка — не наказание и в историю не пишется, но в
аудит попадает.

### п.11 + п.34 Репорты [А][М][В]

**Схема.** `player_reports (id, reporter_id, target_id, game_server_id, reason,
world, x, y, z, created_at, status, claimed_by, claimed_at, resolved_at,
resolution, punishment_id)`.

**В игре:** `/report <ник> <причина>` с кулдауном (одна жалоба в минуту, три в
час) — иначе репорт становится способом спамить стаффу. Координаты и мир
снимаются автоматически: без них «он гриферит» непроверяемо.

**Стаффу:** сигнал онлайн-модераторам сразу, `/reports` — список открытых,
`/reports claim <id>` — взять в работу, `/reports tp <id>` — телепорт к месту.

**В админке:** очередь со статусами, связка с выданным наказанием.

**Обратная связь репортеру** — обязательна: закрытый репорт показывается автору
при следующем входе. Механика уже существует у `pending_warns` (показ + `ack`),
переиспользуется целиком. Без этого жалобы перестают писать через месяц.

Права: `noro.mod.reports.view`, `.claim`, `.resolve`.

### п.10 Автомодерация чата [А][М][В]

**Режим — на каждый фильтр** (решено): `deny` (не пропустить сообщение),
`escalate` (отказ, при повторе в окне — мут), `punish` (мут сразу),
`shadow` (пропустить, сообщить стаффу). Плюс `enabled`.

**Фильтры:**

| Фильтр | Как считает |
| --- | --- |
| Реклама | IP-адреса, домены, discord-инвайты; белый список своих доменов из админки |
| Мат | Словарь из админки, по нормализованному тексту |
| Капс и флуд | Доля заглавных, повтор сообщения, скорость отправки — пороги в админке |
| Обход | Не фильтр, а **нормализация до проверки**: гомоглифы кириллица/латиница, leet (`4`→`ч`), разрядка `п р и в е т` |

**Где живёт код.** В `core`, с оглядкой на правило «≤150 строк на файл»:
`ChatFilters` (набор и решение), `TextNormalize` (нормализация),
`AdRule`, `WordRule`, `CapsRule`, `FloodRule`, `FilterConfig` (модель конфига).

**Как наказывает.** `POST /api/agent/players/{uuid}/punishments` **без**
`actor_uuid` — путь автомодерации, который на мастере уже реализован и сейчас
не используется никем: прав у сервера нет, действуют только рамки указанного
пункта свода, снимать наказания он не может. Ничего нового на мастере для
выдачи не требуется — только конфигурация фильтров.

**Хранение текста.** Сохраняется **только сообщение-триггер** в записи о
срабатывании — как доказательство. Общий чат-лог мы сознательно не ведём.

**Готово, когда:** реклама режется, `п р и в е т с 1 2 7.0.0.1` ловится
нормализацией, ложное срабатывание видно стаффу в shadow-режиме до включения
наказаний, а мут выдаётся по пункту свода с его же формулировкой.

### п.43 Ваниш [А][М][В][Л]

Единственный пункт плана, который **приносит в агент микшины**. До сих пор их не
было ни одного, и в `agents.md` прямо записано, что для перехвата чата на старых
Fabric их тащить не стали. Здесь решение обратное — и вот почему.

**Требование задано жёстко:** «его как будто нету на сервере, вообще ничего на
него не триггерится, даже модовые штуки». Пакетное скрытие такого не даёт: оно
обманывает клиент, но сервер продолжает считать игрока присутствующим — мобы
агрятся, сенсоры срабатывают, моды находят его в списках. Честный ваниш живёт на
уровне выборки сущностей, а туда без микшина не попасть.

#### Решения

| Тема | Решение |
| --- | --- |
| Реализация | Микшины на модах; на Paper — родное `hidePlayer` |
| Кто видит | Право `noro.mod.vanish.see` **и** вес роли не ниже: админ видит ваниш модератора, модератор админа — нет |
| Отключается | Подбор предметов, агрессия мобов, триггеры блоков, урон и голод — плюс невидимость для всего, что ищет игроков в мире |
| Запрещено | Ломать и ставить блоки, бить сущности |
| Чат | Сообщение из ваниша уходит только стаффу, не в общий чат |
| Сундуки | Открываются тихо: без анимации крышки и звука |
| Онлайн | Нет ни в табе, ни в числе; **сессия при этом пишется** |
| Сообщения о входе/выходе | Фейковый выход при включении, вход при выключении — **штатным путём сообщения**, чтобы чат-мод отформатировал его как настоящий |
| Вход в ванише | Флаг «войти тихо» в лаунчере, видимый только при наличии права |

#### Точки микширования

Минимальный набор, покрывающий требование. Каждая — риск на 46 модовых сборках,
поэтому список короткий сознательно:

| Цель | Куда |
| --- | --- |
| Не виден и не трекается | `ChunkMap.TrackedEntity#updatePlayer` |
| Нет в табе | Фильтр player-info в `PlayerList#broadcastAll` |
| Мобы и **моды** не находят | `ServerLevel#getPlayers(Predicate)`, `Level#getNearestPlayer(…)` |
| Блоки-триггеры молчат | `Level#getEntities(…)` — плиты, сенсоры и sculk ходят через него |
| Не подбирает дроп | `ItemEntity#playerTouch` |
| Тихий сундук | `ContainerOpenersCounter#incrementOpeners` |

Всё остальное делается **без** микшинов, штатными средствами: запрет ломать,
ставить и бить — событиями, которые есть на всех платформах (Fabric API
`PlayerBlockBreakEvents`, `UseBlockCallback`, `AttackEntityCallback`; Forge и
NeoForge — `BlockEvent`, `PlayerInteractEvent`; Paper — свои). Неуязвимость —
ванильным `setInvulnerable(true)`, сытость — удержанием значения.

#### Онлайн и сессии

Heartbeat начинает нести **два** списка: `players[]` — видимые, `vanished[]` —
скрытые. Публичное число онлайна считается по первому, сессии из п.6 пишутся по
обоим. Иначе получилось бы одно из двух: либо часы дежурства модератора
пропадают, либо мастер решает, что скрытый игрок вышел, и закрывает сессию по
реконсиляции.

Число в ping-ответе сервера (то, что видно в списке серверов клиента) тоже
уменьшается: на Paper — событием пинга, на модах — микшином рядом с остальными.
«Онлайн 1, а в мире никого» выдаёт наблюдателя быстрее любой ошибки трекинга.

#### Фейковый выход

Своего текста агент не пишет. Он прогоняет штатное ванильное сообщение
(`multiplayer.player.left` / `.joined`) тем же путём, которым его рассылает
сервер, — и чат-мод, перехватывающий этот путь (у нас StyledChat), форматирует
его как настоящий выход. Полноценное событие выхода не вызываем: остальные моды
решат, что игрок ушёл, сохранят данные и закроют ему меню.

#### Вход в ванише

Автованиша по состоянию **нет**: вместо него в лаунчере — флаг «войти тихо»,
который показывается, только если у игрока есть право. Флаг едет на мастер, тот
кладёт его в профиль, агент применяет ваниш до появления в мире.

Отдельно от флага: если ваниш был включён в момент выхода, он восстанавливается
при следующем входе — состояние живёт на мастере (`player_vanish`), как и
заморозка, и переживает рестарт сервера.

#### Прозрачность

Включение и выключение ваниша всегда пишется в аудит, а список тех, кто сейчас
скрыт, виден в админке и по `/vanish list` тем, у кого есть право видеть.
Невидимость для игроков — да; невидимость для журнала — нет.

**Готово, когда:** модератор в ванише не виден в мире, табе и на сайте; зомби
проходит мимо; нажимная плита не срабатывает; дроп не подбирается; сундук
открывается без анимации; в чате виден обычный «X вышел из игры» в оформлении
чат-мода; а другой модератор с ролью выше — видит его с пометкой.

## Волна 4. Эксплуатация

### п.17 + п.37 Расписание рестартов [М][В][А][W]

**Схема.** `restart_schedules (id, game_server_id, enabled, mode, at_times[],
interval_minutes, cron, timezone, online_policy, grace_minutes,
max_defer_minutes, backup_before, next_run_at, last_run_at)`.

**Два режима задания** (решено): простой конструктор («в 05:00 и 17:00» либо
«каждые 6 часов») и сырой cron — переключателем, для редких случаев вроде
«только по будням».

**Политика при онлайне — на каждое расписание** (решено):

- `warn_and_go` — обратный отсчёт и рестарт в назначенное время;
- `defer` — ждать окна с нулевым онлайном, но не дольше `max_defer_minutes`,
  после чего рестарт с предупреждением.

Ночной и дневной рестарты обычно требуют разного, поэтому политика лежит у
задания, а не у сервера.

**Обратный отсчёт [А].** Кадр `restart_notice` → объявления за 15/5/1 минуту и
за 10 секунд, actionbar на последней минуте, текст — из шаблонов админки.
Сейчас плановый рестарт выглядит для игрока как вылет.

**Кто исполняет.** Планировщик — на мастере (он и так живёт постоянно, а
враппер может быть перезапущен). Мастер шлёт `restart_notice` агенту и
`power restart` враперу.

### п.38 Бэкап без битых регионов [А][W][М]

`ServerBackups.create` пакует мир живого сервера — регионы дописываются в
момент упаковки, и часть бэкапов оказывается битой ровно тогда, когда нужна.

Перед упаковкой: `save-off` + `save-all flush`, после — `save-on`. Отдать эти
команды может только агент **внутри** игры; враппер снаружи знает лишь про
процесс. Значит бэкап становится согласованной операцией: мастер просит агента
подготовить мир, ждёт подтверждения, запускает упаковку у враппера, потом
разрешает сохранение обратно.

**Обязательно:** `save-on` возвращается и по таймауту, и при обрыве связи, и
при падении упаковки. Сервер, оставшийся с выключенным автосохранением, теряет
всё с последнего сохранения — это опаснее битого бэкапа.

### п.39 Зависание сервера [А][М][В]

**Просадка TPS — только алерт** (решено): запись в телеметрию, отметка в
админке, сигнал стаффу. Автомат, рестартующий сервер по просадке, однажды
сделает это в разгар ивента.

**Полное зависание — рестарт.** Признак: `TickMeter.stalledSeconds()` больше
порога (по умолчанию 60), то есть игровой поток не двинулся ни разу. Спорить
тут не с чем — сервер уже не отвечает игрокам. Кадр `tick_stall` уходит с
фонового потока, мастер даёт враперу `power restart`.

Включается на каждый сервер отдельно, по умолчанию выключено.

### п.40 Причина падения [W][М][В]

`exit_code` до админки доезжает, но `OutOfMemoryError`, срабатывание watchdog и
crash-loop в нём неразличимы.

Враппер уже читает stdout построчно (`ServerProcess`, `onLine`) — добавляется
кольцевой буфер последних 200 строк и распознавание причины по шаблонам:
`OutOfMemoryError`, `A single server tick took` / watchdog, «не стартует»
(падение раньше `CRASH_LOOP_SECONDS`, эта логика в `ExitWatcher` уже есть).

В кадре статуса появляется `exit_reason` и хвост лога; админка показывает
причину строкой вместо «код 1».

### п.25 Техработы [А][М][В]

**Выбор в момент включения** (решено): «закрыть вход» либо «закрыть и выгнать».
Перед горячим фиксом нужно первое, перед миграцией мира — второе.

Состояние — колонки в `game_servers` (`maintenance`, `maintenance_message`).
Проверка — в `AccessGate`, рядом с `allowed`; проходит тот, у кого есть
`noro.server.maintenance.bypass`. Текст отказа — шаблон из админки.

**Важно:** решение о техработах принимает мастер и отдаёт готовым флагом, как
`allowed`. Дублировать это в трёх реализациях агента нельзя — правило из
`agents.md`, и оно здесь действует ровно так же.

## Волна 5. Доступ

### п.24 Флаг целостности на входе [А][М]

**Исполняется действие из `blocked_files`** (решено), градация уже есть в
`schema::BlockAction`:

- `BlockLaunch` — не пускать в игру, пока файл на месте;
- `Flag` — пустить и сообщить стаффу (пометка в `/check` и в списке онлайна);
- `Delete` — ничего, лаунчер уже удалил файл.

Считает мастер и кладёт в профиль готовым вердиктом (`integrity`), агент
исполняет. Причина та же, что у `allowed`: правило живёт в одном месте.

**Что это на самом деле.** Единственная честная связка «лаунчер → игра» из
существующих: она не проверяет, каким клиентом играет человек (это, как сказано
в `agents.md`, недостижимо), а сверяет то, что лаунчер уже увидел на диске.
Обещать ею защиту от читов нельзя, ловить known-файлы — можно.

## Отдельная дорожка: принудительные действия лаунчера [М][Л][В]

Требование: действия над лаунчером (закрыть игру, перезапустить, переустановить
сборку, снести кэш) должны иметь вариант **без запроса подтверждения** у игрока.

Сейчас `RemoteAction::needs_confirmation()` (`crates/schema/src/integrity.rs:116`)
требует подтверждения для всего, кроме `VerifyIntegrity`. Образец нужного
поведения в проекте уже есть: у `LogRequest` есть флаг `forced` и отдельное
право на сбор логов без согласия.

**Как делаем:**

1. `RemoteAction` в `ServerWsMsg` получает поле `forced: bool`.
2. **Своё право на каждое действие** (решено):
   `noro.launcher.remote.kill_game.force`,
   `noro.launcher.remote.restart_launcher.force`,
   `noro.launcher.remote.reinstall_build.force`,
   `noro.launcher.remote.clear_asset_cache.force`.
   Мастер проверяет право **до** отправки кадра; лаунчер, получив `forced`,
   исполняет без диалога.
3. **Уведомление — галка админа в момент действия** (решено): по умолчанию
   игрок видит постфактум «игра закрыта администратором X: причина». Снять
   галку можно только с правом `noro.launcher.remote.silent` — чтобы тихий
   режим оставался исключением, а не привычкой.
4. Причина обязательна для любого `forced` и попадает в аудит вместе с тем, кто
   действовал и была ли галка «тихо».

**Почему право на каждое действие, а не одно общее.** «Закрыть игру» и
«переустановить сборку» — разные по цене ошибки: первое отнимает у игрока
текущую сессию, второе — час на скачивание. Раздавать их одним узлом значит
выдавать второе тому, кому нужно только первое.

## Ограничения, о которых надо помнить

- **Fabric ниже 1.19.1 — чат не перехватить.** Ни мут, ни автомодерация там не
  работают: `fabric-message-api` появился только с подписанным чатом, а тащить
  свой микшин в тридцать сборок дороже пользы. Это уже задокументировано в
  `FabricEntry.java:42` и остаётся в силе.
- **На Fabric команды блокируются только «говорящие».** `ALLOW_COMMAND_MESSAGE`
  ловит не все команды, поэтому заморозка там держится якорем позиции, а не
  запретом `/home`.
- **80 сборок.** Любой новый вызов Minecraft API проверяется на всём диапазоне
  1.18.2 → 26.x. Именно поэтому TPS считается своим счётчиком тиков, а
  неуязвимость ставится ванильным `setInvulnerable`.
- **Микшины появляются впервые — и только ради ваниша.** Их нет ни одного, и
  вводить их дорого: конфиг микшинов на каждый лоадер, шесть точек по внутренним
  классам сервера, 46 модовых сборок от 1.18.2 до 26.x, где эти классы менялись.
  Ошибка микшина роняет сервер на старте, а не выдаёт красную строку в логе.
  Поэтому ваниш делается **последним в своей волне**, начинается с одной целевой
  версии (NeoForge 1.21.1 — на ней стоит боевая сборка), и только после живой
  проверки раскатывается на диапазон. Если какая-то точка не переносится на
  старые версии — там ваниш выключается, а не чинится ценой директив в каждой
  сборке.
- **Отказ во входе на Fabric и NeoForge приходит после входа в мир** — пред-логин
  хука без микширования там нет. Касается техработ и целостности: игрок увидит
  мир на секунду. В прокси-топологии проверку правильнее ставить на прокси.
- **Объём данных.** Сессии, телеметрия и срабатывания фильтров растут линейно от
  онлайна. У каждой таблицы должен быть срок жизни, заданный вместе с миграцией,
  а не «потом».
- **Приватность.** Общий чат-лог мы сознательно не ведём: хранится только
  сообщение-триггер автомодерации. IP игрока, если он появится в событиях входа,
  хранится хешем.
