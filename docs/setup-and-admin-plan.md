# План: первичная настройка, root-доступ, работа с игроком

> **Статус: ничего из этого не реализовано.** Файл описывает намерение, а не
> текущее поведение. Всё, что уже работает, отмечено в §1 и в ссылках на код.
>
> **Ветка работ: `feat/setup-and-admin`** (создана от `master` на `53b031e`).
> Все фазы этого плана делаются в ней, не в `master`. Перед началом:
> `git checkout feat/setup-and-admin`.
> Ветка длинная и охватывает несколько независимых фаз — коммиты дробить по
> этапам из §12 (`2.2`, `0.1`, `S2`, …), чтобы её можно было выпускать частями,
> а не одним куском.

Модель сети — закрытая, как у GravitLauncher: игрок не ходит на чужие серверы и
не ставит произвольные моды, только опциональные из выданного списка. Игровой
каталог выдан сетью, личного в нём почти ничего нет, поэтому хеши файлов и логи
— в первую очередь антифрод-сигнал, и лишь во вторую поддержка.

## 2. Дефекты, найденные при проектировании

Не новые фичи — расхождение кода с уже заявленной моделью. Чинятся независимо
от остального плана.

### 2.1 Passkey-вход не проверяет ничего

`crates/master/src/api/auth/passkeys.rs:159` (`login_verify`) и `:282`
(`passkey_launcher_verify`) принимают `credential_id`, находят по нему запись и
сразу выдают сессию. Подпись WebAuthn не проверяется, `public_key` и `counter`
не используются. `credential_id` — публичное значение, его отдаёт браузер.

Следствие: кто узнал `credential_id` — вошёл в аккаунт. Второй эндпоинт сразу
выдаёт launcher-код, то есть и игровую сессию.

Чинится переходом на `webauthn-rs` с проверкой challenge, origin, rpId и
счётчика.

**Решение по существующим ключам: удалить молча в миграции.** Материала для
проверки в них нет; оставить — значит оставить обходной путь мимо новой
проверки. Вход через Discord у всех сохраняется, так что никто не теряет доступ.

### 2.2 Limited-моды приезжают всем

`crates/master/src/manifest.rs:139` кладёт в манифест весь список
`optional_mods`, включая `limited: true`, а их файлы лежат в `verified_files` —
скачиваются каждому. Проверка права `noro.optional.<server>.<name>` живёт только
в клиенте. `ClientWsMsg::SetOptionalMods` (`api/launcher.rs:279`) — пустая ветка
с комментарием «здесь можно записывать для статистики».

Следствие: файлы ролевого мода уже на диске у любого игрока, а решение
«включать или нет» принимает клиент. Репозиторий открыт (MIT) — свой билд
включит что угодно.

**Решение: фильтровать на уровне манифеста.** Нет права — нет ни мода в списке,
ни его файлов в `verified_files`. Манифест и так собирается персонально и
подписывается. Единственный вариант, при котором пропатченный клиент бессилен:
файла просто нет на диске.

Побочный эффект: при выдаче права игроку нужен ре-синк для докачки. Это
приемлемо — выдача прав редка. `clean_extra` при этом сам удалит файлы мода при
отзыве права, что даёт корректное поведение в обе стороны.

### 2.3 Целостность проверяется только в момент синка

`clean_extra` (`backend/src/sync/file_sync.rs:245`) удаляет посторонние файлы во
время синка. Между синком и запуском, и во время игры каталог не
перепроверяется. Плюс маски в `unmanaged_paths` (`xaero*` из миграции 0022) —
штатно защищённые от удаления пути.

Решение — в §7.1.

### 2.4 Admin-токены хешируются SHA-256 без соли

`api/auth/middleware.rs:86`. INSTRUCTIONS §18.4 обещает Argon2. Привести код к
доке, добавить распознаваемый префикс `noro_at_…`.

## 3. Принятые решения

| Развилка | Решение |
|---|---|
| Доставка impersonation-токена | WS + подтверждение в лаунчере; фолбэк — ручной код. **Не** `noro://` |
| Хранение секретов | секреты остаются в env; в БД — только несекретные настройки |
| Вход root-аккаунта | passkey + recovery-коды. Пароля и TOTP нет |
| Применение настроек | **рестарт мастера**, без hot-reload и `ArcSwap` |
| Существующий прод | env → БД переносится автоматом при первом старте |
| Limited-моды | фильтруются из манифеста вместе с файлами |
| Найден лишний файл | удалить и запустить, флаг админу |
| Существующие passkeys | удалить молча |
| Игра под impersonation | разрешена, с пометкой в Yggdrasil |
| Уведомление игрока об impersonate | не уведомлять |
| Права под impersonation | полный доступ (два исключения — §8.2) |
| Кого можно impersonate | только тех, чьи права — подмножество своих |
| Step-up без passkey | одноразовый recovery-код |
| Служебный вход в лаунчере | не делаем, только «Login as» из веба |
| Сбор логов | модалка с согласием + принудительный режим по отдельному праву |
| Retention | бандлы 30 дней; аудит и журнал запусков бессрочно |
| Discord-webhook | не делаем, хватает `audit_log` |
| Режимы синхронизации | четвёртый режим `merged`, three-way по хешам (§10.5) |
| Списки путей | схлопнуть в упорядоченные `path_rules`, побеждает последнее совпавшее |
| Запрещённые файлы | своя база, приоритет выше всех path-правил, внутри подписанного манифеста |

## 4. Фаза 1 — первичная настройка

### 4.1 Что куда переезжает

**Остаётся в env навсегда:** `DATABASE_URL`, `NORO_BIND`, `NORO_DATA_DIR`,
`SENTRY_DSN` (нужен до подъёма БД), и все секреты — `DISCORD_CLIENT_SECRET`,
`GITHUB_TOKEN`, `NORO_SIGNING_KEY`, `S3_*`, `CURSEFORGE_API_KEY`.

**Переезжает в БД:** публичные URL, CORS-origins, `DISCORD_CLIENT_ID`, pubkey
подписи, имя инстанса, флаги, лимиты, настройки лаунчера.

Схема: `instance_settings(key TEXT PK, value JSONB, updated_at, updated_by)` и
`instance_state(setup_completed BOOL, setup_token_hash, …)`.

Приоритет чтения: **env > БД > дефолт**.

### 4.2 Настройки применяются рестартом

`Config` читается один раз при старте, как сейчас — меняется только источник
(БД вместо env). `AppState` не трогаем, `ArcSwap` не вводим: это сжимает фазу
примерно вдвое, потому что `Config` торчит в мастере повсюду.

Цена: рестарт рвёт WS-соединения лаунчеров (переподключатся сами, backoff уже
есть) и обрывает активные загрузки файлов у тех, кто в этот момент синкается.
Поэтому админка после сохранения показывает «требуется перезапуск» и не делает
его сама — момент выбирает оператор.

### 4.3 Визард двухфазный

Прямое следствие решения «секреты только в env»: визард физически не может
дописать `DISCORD_CLIENT_SECRET` и `NORO_SIGNING_KEY`.

```
Фаза A — мастер поднят с одним DATABASE_URL
  setup_completed = false → всё API кроме /api/setup/* и /health отдаёт
  503 setup_required; Nuxt-middleware редиректит на /setup

  вход по одноразовому токену из $NORO_DATA_DIR/setup-token.txt
  (он же печатается в лог при старте — модель Jenkins initialAdminPassword)

  шаги:
    · URLs (public/web), CORS, имя инстанса      → в БД
    · Discord: client_id                          → в БД
               client_secret                      → блок «добавьте в .env»
               показ redirect-URI для портала
    · Подпись: кнопка «сгенерировать ed25519»
               приватный seed показывается ОДИН раз → в .env
               pubkey                              → в БД + команда сборки лаунчера
    · финал: собранный блок .env целиком, кнопка «копировать»

  → экран «перезапустите мастер»

Фаза B — после рестарта
  визард видит секреты в окружении, «проверить Discord» делает реальный запрос
  → создание root-аккаунта (§5)
  → setup_completed = true, setup-токен сожжён, файл удалён
```

Приватный ключ подписи, показанный визардом, **нигде не сохраняется** — ни в
БД, ни в логе. Не скопировал — генерируется заново. После первой подписанной
сборки кнопка блокируется и требует процедуру ротации.

### 4.4 Миграция существующего инстанса

При старте: `setup_completed = false`, `instance_settings` пуст, но в env заданы
`NORO_PUBLIC_URL` и `DATABASE_URL` → мастер копирует несекретные значения из env
в БД, ставит `setup_completed = true` и пишет об этом в лог. Боевой инстанс
перехода не замечает и никогда не видит `503 setup_required`.

## 5. Фаза 2 — root-аккаунт без Discord

Миграция: `users.discord_id` → nullable, `CHECK (discord_id IS NOT NULL OR
is_local_account)`. Новые поля: `is_local_account`, `recovery_codes` (argon2,
одноразовые).

Ограничения root: не может быть забанен, не может удалить сам себя,
`mc_uuid`/`mc_username` генерируются, но **по умолчанию без права входа в игру**
— это операторский аккаунт.

### Способы входа

- **Passkey** — основной. Требует §2.1 как жёсткого предусловия.
- **Recovery-коды** — 10 штук, argon2, одноразовые, показываются в визарде и
  скачиваются файлом.

### Почему recovery-коды здесь не «аварийный вариант»

WebAuthn не работает по `http://` на не-localhost адресе. Инстанс на
`http://<ip>:8080` — типовой первый запуск — **не даст привязать passkey
вообще**. Раз пароля в модели нет, recovery-коды остаются единственным входом до
настройки домена и TLS.

Поэтому:
- вход по recovery-коду даёт **полноценную** сессию; ведёт на экран «привяжите
  passkey» и пишется в аудит;
- визард детектит небезопасный контекст (`http://` + не localhost),
  предупреждает и разрешает пропустить шаг с passkey;
- перевыпуск кодов доступен из кабинета при живой сессии, старые сгорают разом;
- при остатке ≤ 3 кодов — предупреждение в админке.

## 6. Фаза 3 — настройки в админке

Страница `/admin/settings`, секции повторяют шаги визарда: General, Auth,
Signing, Storage, Integrations, Launcher, Maintenance.

- секретные поля read-only: `DISCORD_CLIENT_SECRET · задано в окружении` либо
  `не задано — интеграция выключена`. Значение не показывается никогда, даже
  маской длины;
- запись требует права `noro.admin.settings`, каждое изменение → `audit_log` с
  diff;
- после сохранения — баннер «требуется перезапуск мастера» (§4.2);
- **Diagnostics**: dev-ключ подписи? CORS пустой? Discord отвечает? CDN живой?
  Сейчас «прод на dev-ключе» видно только строчкой в логе при старте;
- «экспортировать как .env» — чтобы конфиг можно было увезти обратно в compose.

## 7. Фазы 6a–6c — работа с игроком

Разделение, без которого фича не работает:

| | Поддержка | Расследование |
|---|---|---|
| Игрок | хочет помощи | не хочет быть пойманным |
| Согласие | уместно, снижает тревогу | бессмысленно — нажмёт «Отклонить» |
| Что нужно | полный бандл логов | хеши файлов и список загруженных модов |

### 7.1 Фаза 6a — integrity-телеметрия (без согласия)

Собирается автоматически при каждом запуске игры. **Объявляется заранее** — в
правилах сети и на первом входе в лаунчер.

- SHA1 файлов в managed-путях → сверка с подписанным манифестом;
- фактически загруженные моды — Fabric/Forge печатает список при старте,
  парсится из лога;
- какие опциональные моды включены и есть ли на них право;
- версия лаунчера, подпись его бинарника.

**Реакция на расхождение: удалить лишнее и запустить, флаг админу.** То же, что
делает `clean_extra`, но ещё раз непосредственно перед запуском, плюс отчёт
мастеру. Игрок видит нейтральное «восстановлены файлы сборки»; админ — флаг с
подробностями (`mods/xaeroplus.jar — нет в манифесте`, `включён limited-мод без
права`).

Логика выбора: честный игрок (битый диск, антивирус съел файл) ничего не
замечает и продолжает играть, а тот, кто подкладывал мод намеренно, не получает
явного сигнала «здесь есть проверка, обходи её вот тут». Цена — повторная сверка
хешей добавляет задержку перед запуском; считать только по managed-путям и
кэшировать по mtime+size.

Сюда же — вынос `redact()` из `log_reader.rs` в отдельный
`backend/src/redact.rs` (исходный файл близок к лимиту 150 строк).

### 7.2 Фаза 6b — support bundle

**Два режима:**

- **С согласием** (по умолчанию) — модалка у игрока, как описано ниже.
- **Принудительно** — отдельное право `noro.admin.support.logs.force`,
  обязательная причина, бандл забирается без спроса. Нужен ровно там, где
  согласие бессмысленно: иначе единственный, чьи логи никогда не придут, —
  читер. Каждое применение — в `audit_log` отдельным типом события.

**Состав.** Фиксированный allowlist в коде, не «всё из папки»:
`logs/latest.log` + N последних `*.log.gz`, `crash-reports/*.txt` (последние 3),
`hs_err_pid*.log`, лог лаунчера, `options.txt`, список модов и опциональных
тумблеров, environment-манифест (ОС, RAM, GPU, JVM, диск, версия сборки),
результат сверки с манифестом.

Не собирается: `saves/`, `screenshots/`, `servers.dat`.

**Поток режима с согласием:**

```
Админ (веб, карточка игрока)
  → «Запросить логи», обязательное поле «зачем» — уходит игроку и в аудит
  ↓
Мастер: log_requests(id, actor, target, reason, scope, forced, expires_at, status)
        WsHub.send_to_user(target) → ServerWsMsg::LogRequest
  ↓
Лаунчер: модалка — кто, зачем, список файлов с размерами,
         кнопка «Посмотреть, что отправится», таймер 5 минут
  ↓ (Отправить)
Лаунчер: собрать → санитизировать → gzip → POST /api/launcher/support-bundle
  ↓
Мастер: второй проход санитизации на своей стороне,
        FileStore.put_bytes, support_bundles(sha1, expires_at), аудит
  ↓
Веб: лог-вьювер (фильтр по уровню, поиск, ссылка на строку) + скачивание
```

Кнопка «Посмотреть, что отправится» показывает ровно тот текст, который уйдёт —
после санитизации. Без неё фича неотличима от слежки; с ней игрок видит
`C:\Users\*****` вместо своего имени.

Второй проход санитизации на мастере обязателен: клиент можно подменить, и логи
от подменённого клиента не должны попасть во вьювер с токенами.

**Санитизация — что доделать.** Существующие правила рассчитаны на строку в
кавычках из log4j. Нужны:
- `Command Line:` из `hs_err` — там **полная командная строка с `--accessToken`**,
  то есть живой Yggdrasil-токен. Это утечка в сторону сети, а не от неё: токен
  ляжет в БД и будет виден всем, у кого есть доступ к вьюверу;
- UUID-подобные значения рядом с `token`/`session`/`Bearer`;
- Discord id, `mc_uuid`;
- IP → `203.0.113.***`;
- **тест-корпус**: реальный `hs_err`, реальный `latest.log` с Fabric и
  authlib-injector, лог лаунчера. Тест «ни один известный формат токена не
  проходит наружу» здесь обязателен.

**Хранение.** Право `noro.admin.support.logs`, отдельное от `*`. Бандлы живут 30
дней, дальше `files/gc.rs` подберёт осиротевший blob. Игрок видит в кабинете
свои бандлы и может удалить те, что отправил добровольно; принудительно
собранные не удаляются.

**Инициатива игрока важнее.** Кнопка «Сообщить о проблеме» и авто-предложение
после краша используют тот же сборщик, но без запроса, грантов и TTL. Покрывает
большую часть случаев, ради которых нужен админский запрос. Делать первой.

### 7.3 Фаза 6c — диагностика и удалённые действия

`ClientWsMsg::DiagnosticsReport` по запросу: версии, JVM, RAM/диск, целостность,
скорость до мастера и CDN, последняя ошибка синка. Личного нет → согласие не
нужно. Закрывает половину тикетов «не запускается» без единого файла.

Удалённые действия с подтверждением: «проверить целостность», «очистить кэш
ассетов», «переустановить сборку», «перезапустить лаунчер».

## 8. Фазы 4–5 — impersonation и статус лаунчера

### 8.1 Модель

`POST /api/admin/users/{id}/impersonate` → `impersonation_grants(id, actor_id,
target_id, reason, created_at, expires_at, consumed_at, revoked_at)`. Сессия
наследует `impersonated_by` в `oauth_sessions`.

### 8.2 Правила

- право `noro.admin.impersonate`, **отдельное от `*`**;
- **цель — только пользователь, чьи права строго подмножество прав актора.**
  Админа нельзя «надеть» через другого админа. При выбранном полном доступе это
  единственная преграда против эскалации привилегий, так что правило жёсткое и
  проверяется на сервере при каждом гранте;
- **step-up re-auth**: passkey не старше 5 минут. Если passkey недоступен
  (инстанс на `http://` без домена) — одноразовый recovery-код. Чтобы 10 кодов
  не сгорели за 10 входов, успешный step-up открывает окно 15 минут, внутри
  которого дополнительный код не запрашивается;
- **обязательное `reason`**, уходит в аудит;
- **нет вложенности**: сессия с `impersonated_by` не выдаёт новых грантов и не
  рефрешится;
- TTL сессии 30–60 мин, одноразовый код гранта живёт 60 секунд;
- **права: полный доступ** — админ может всё, что может игрок. Два исключения,
  и оба не про удобство, а про необратимость:
  - **привязка passkey** — переживёт сессию и станет постоянным входом в чужой
    аккаунт;
  - **удаление аккаунта** — необратимо;
- вход в игру разрешён, Yggdrasil-профиль помечается, `hasJoined` отдаёт флаг —
  в логах игрового сервера видно, кто зашёл на самом деле;
- **игрок не уведомляется** — ни пушем, ни записью в кабинете;
- баннер в лаунчере админа: «Вы в аккаунте X от имени администратора · Выйти».

### 8.3 Аудит под impersonation — детальный

Прямое следствие двух решений: полный доступ + отсутствие уведомления. В игровых
логах и в истории аккаунта действия админа неотличимы от действий игрока, и
разрешить спор («меня обокрали» / «это был не я») можно будет только изнутри.

Поэтому под impersonation в `audit_log` пишется **не факт входа, а каждое
действие**: метод, путь, идентификатор объекта, краткий diff изменения. Вне
impersonation такой детализации не нужно — там достаточно событий уровня
«изменил роль», «выкатил версию».

### 8.4 Поток «Login as» через WS

```
Веб: POST /impersonate {reason} → проверка step-up, подмножества прав
  ↓
Мастер: грант, WsHub.send_to_user(actor_id, ImpersonateRequest{...})
  ↓
Лаунчер админа: модальный диалог с именами и причиной, отсчёт 60 сек
  ↓ (подтверждено)
Лаунчер: POST /api/launcher/impersonate/claim своим текущим Bearer
  ↓
Мастер: грант сожжён, токены отданы по HTTPS → лаунчер перелогинивается
  ↓
Веб: поллинг GET /api/admin/impersonate/{grant_id} раз в секунду
```

Токен уходит по уже аутентифицированному каналу лаунчера — не через браузер, не
через URL, не через аргументы процесса (их видно в `ps` любому процессу на
машине). Нативный диалог — второй фактор: закрывает случай «злоумышленник
получил веб-сессию админа, но не доступ к его машине».

Фолбэк, если лаунчер не в сети: код на 60 секунд, вводится в лаунчере в поле
«Код входа». **Полноценного экрана «Служебный вход» с отдельной аутентификацией
не делаем** — точка входа одна, из веба; в лаунчере только диалог подтверждения
и поле для фолбэк-кода. Меньше GPUI-кода и меньше поверхности атаки.

**Протокол** (`crates/schema/src/ws_protocol.rs`):

```rust
ServerWsMsg::ImpersonateRequest {
    grant_id: Uuid,
    actor_username: String,
    target_username: String,
    reason: String,
    expires_at: DateTime<Utc>,
}
ClientWsMsg::ImpersonateResponse { grant_id: Uuid, accepted: bool }
```

### 8.5 Фаза 5 — статус лаунчера

`GET /api/admin/users/{id}/launcher`: онлайн (нужен `WsHub::is_user_connected`),
версия/платформа/last_seen из `launcher_clients`, актуальность версии, текущий
запущенный сервер. На карточке: индикатор, версия с бейджем «устарел», кнопки
`Login as`, `Запросить логи`, `Отправить уведомление`, `Завершить все сессии`.

## 9. Смежное — всё в работе

**Наказания.** `punishments(id, user_id, kind, reason, actor, created_at,
expires_at, revoked_at)`: временные баны, история, автоснятие по истечении,
ограничение доступа к отдельному серверу вместо тотального бана, предупреждение
с обязательным подтверждением прочтения перед входом в игру. Кик — через
агентский канал. Существующие `users.banned`/`ban_reason` мигрируют в первую
запись и остаются как денормализованный кэш либо убираются совсем.

**Журнал запусков.** `ReportGameStart/Stop` уже есть, но хранит только playtime.
Дописать снапшот на момент запуска: сборка, версия лаунчера, набор опциональных
модов, integrity-статус. Расследование становится возможным задним числом.
Хранится бессрочно — строки лёгкие.

**Управление сессиями.** Список активных (устройство, IP, дата,
impersonation-флаг), «завершить», «завершить все кроме текущей». Сейчас отозвать
скомпрометированный токен нечем.

**Заметки и объявления.** Внутренние заметки на карточке игрока (автор, дата,
видны только админам) и таргетированные баннеры по роли, версии лаунчера или
серверу — механизм рассылки уже есть.

**Onboarding-чеклист** после setup: создать сервер → импортировать сборку →
выкатить версию лаунчера → настроить CDN.

**Maintenance mode** — баннер, блокировка входа в игру, исключение для админов.

## 10. Синхронизация: режимы, blocklist, инвентарь

Отдельный пласт, не связанный с админкой напрямую, но опирающийся на ту же
машинерию хешей, что и integrity-телеметрия (§7.1).

### 10.1 Текущая модель — три режима

| Режим | Скачивается | Обновляется | Удаляется лишнее |
|---|---|---|---|
| обычный | да | при расхождении хеша | да |
| `user_managed_paths` | один раз, если файла нет (`file_sync.rs:73`) | **никогда** | нет |
| `unmanaged_paths` | нет вообще (исключён из `effective`, `file_sync.rs:42`) | нет | нет |

Главный дефект `user_managed`: сервер обновил конфиг мода — игрок остаётся на
старом навсегда, даже если сам файл никогда не трогал.

### 10.2 Сначала диагностика Xaero

Жалоба «карта стирает все точки каждый перезапуск» **скорее всего не про синк**.
Проверено: маски `xaero*`, `xaeroworldmap*`, `xaerominimap*` есть во всех
сборках в БД; `is_protected` их матчит (покрыто тестами в
`file_sync_tests.rs`); `--gameDir` указывает ровно на `instance_dir`
(`game_runner/args.rs:134`), то есть Xaero пишет в корень инстанса, куда маска и
применяется. Эти файлы исключены из `effective` — синк их не трогает.

Рабочая гипотеза: Xaero хранит waypoints в `XaeroWaypoints/Multiplayer_<id
сервера>/`, а `servers_dat.rs` переписывает `servers.dat` перед каждым запуском.
Меняется запись сервера — Xaero видит «другой сервер» и заводит новую папку.
Файлы на диске целы, но не показываются.

**Проверка до начала работ:** зайти в инстанс после «пропажи» и посмотреть,
есть ли файлы в `XaeroWaypoints/`. Если есть — режимы синхронизации тут ни при
чём, чинить надо стабильность идентификатора сервера в `servers.dat`.

С конфигами модов всё однозначно: `config/*` (кроме `xaero*`) лежит в манифесте
и перезаписывается по хешу. Здесь merge нужен по-настоящему.

### 10.3 База запрещённых файлов

`blocked_files(id, kind, pattern, sha1, reason, action, scope, created_at)` на
мастере, отдаётся **внутри подписанного манифеста** — иначе список подменяется
на клиенте.

**Приоритет выше всех path-правил.** Проверяется и внутри `unmanaged`, и внутри
`user_managed`: в этом весь смысл — папка ресурспаков не синхронизируется, но
xray оттуда удаляется.

| Способ матчинга | Ловит | Обходится |
|---|---|---|
| SHA1 | известные сборки xray-паков | изменением одного байта |
| маска имени (`*xray*`) | ленивых | переименованием |
| «файл не из манифеста» | всё сразу, но шумно | ничем — но это флаг, не удаление |

Честно: SHA1 и маски ловят ленивых, а не мотивированных. Реальный охват даёт
третий пункт, то есть §10.4.

Действия: `delete` (по умолчанию), `flag`, `block_launch`. Проверка при синке и
повторно перед запуском, вместе с integrity-сверкой.

### 10.4 Инвентарь несинхронизируемых папок

Сейчас unmanaged-пути не сканируются вообще. Нужен обход этих путей,
`(path, size, sha1, mtime)` → сравнение с `.noro/inventory.json` от прошлого
запуска → новые и изменённые уходят мастеру как флаг.

Ключевое ограничение — **не хешировать всё подряд**: `saves/` это гигабайты.
Отдельный список `watched_paths` (по умолчанию `resourcepacks/`, `shaderpacks/`,
`mods/`, `config/`), а `saves/`, `logs/`, `screenshots/`, `crash-reports/`
исключены жёстко.

Первый проход помечается `initial`, чтобы админку не завалило флагами при
раскатке.

### 10.5 Четвёртый режим — `merged`

Ядро: **three-way по хешам**, без хранения копий файлов. В
`.noro/base-hashes.json` кладём sha1 того, что установили в прошлый раз.

| `mine` vs `base` | `theirs` vs `base` | Действие |
|---|---|---|
| совпадает | изменился | игрок не трогал → **обновить** |
| изменился | совпадает | сервер не менял → **оставить игрока** |
| изменился | изменился | конфликт → по политике |
| совпадает | совпадает | ничего |

Решает обе половины боли: правки игрока не затираются, но обновления с сервера
доезжают. Стоит дёшево — один json с хешами, никаких копий.

Политика конфликта (настройка сборки): `keep_mine` (по умолчанию, плюс флаг
админу), `take_theirs` (с бэкапом в `.noro/conflicts/<timestamp>/`), `ask`
(диалог в лаунчере).

**Key-level merge** (`.properties`, `.toml`, `.json` — слияние по ключам, а не
по файлу целиком) — это v2. Требует реальной копии base и парсеров форматов, а
конфликт «оба меняли файл, но разные ключи» встречается заметно реже, чем
«сервер обновил, игрок не трогал». Начинать с него не стоит.

### 10.6 Единая модель правил вместо четырёх списков

С четвёртым режимом получается четыре независимых списка путей с неочевидным
приоритетом. Схлопываем в упорядоченный список, как в `.gitignore` — побеждает
**последнее совпавшее** правило:

```json
"path_rules": [
  { "pattern": "config/**",     "mode": "merged" },
  { "pattern": "config/xaero*", "mode": "unmanaged" },
  { "pattern": "saves/",        "mode": "unmanaged" },
  { "pattern": "options.txt",   "mode": "merged" }
]
```

Исключения выражаются естественно, а не разбросаны по трём массивам. Старые поля
мигрируются автоматически: `unmanaged_paths` → правила `unmanaged`,
`user_managed_paths` → `user_managed`. Blocklist остаётся отдельно и всегда
сверху.

`.noro/` добавляется к служебным защищённым путям рядом с `.natives/`,
`.noro-build`, `.noro-servers` (`file_sync.rs:255`).

## 11. Чего не делаем и почему

**Клиентские сигналы не считаем защитой.** Лаунчер открыт (MIT), свой билд
отправит любые хеши. То же ограничение, что и «только мой лаунчер недостижимо».
Практический вывод: **integrity-флаги — повод для ручного разбора, никогда не
автобан.** Автобан по клиентскому репорту даёт ложные срабатывания на честных
(битый диск, антивирус, недокачка) и ноль эффекта против того, ради кого
делался. Настоящая проверка — на игровом сервере, где уже есть агенты: серверная
сторона требует handshake от клиентского мода и сверяет набор модов своим
каналом. Клиентская телеметрия — второй, дешёвый слой.

**Hot-reload настроек** — `Config` торчит в мастере повсюду, `ArcSwap` заденет
много файлов, а часть полей всё равно требует рестарта. Рестарт проще на
порядок.

**URL-схема `noro://`** — код виден в `ps` и в истории браузера, схему может
зарегистрировать любое приложение, нужны три платформенные реализации с нуля.
WS-канал уже есть и надёжнее.

**Отдельный «Служебный вход» в лаунчере** — вторая точка аутентификации ради
сценария, который закрывается фолбэк-кодом.

**Discord-webhook на админские события** — `audit_log` достаточно, а вебхук это
ещё один секрет в env и ещё одна внешняя зависимость.

**Скриншот экрана игрока** — даже с согласием. Захватывает всё окно, включая то,
что игрок не собирался показывать; выгода мизерная против логов.

**Живой стриминг логов** без явного сеанса с постоянным баннером и кнопкой
«прервать».

**HWID** — применимо в закрытой сети (бан по железу, мультиаккаунты), но тоже
обходится своим билдом, и это единственный пункт, реально чувствительный к
приватности. Если делать — объявлять в правилах, хранить соль+хеш, не сырые
серийники. Откладывается до подтверждённой проблемы с обходом банов.
